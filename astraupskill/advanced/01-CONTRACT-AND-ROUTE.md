# 1. Turn the workflow into an observable contract

Begin with [Loan.cs](../../src/BorrowBox.Core/Loans/Loan.cs), [Reservation.cs](../../src/BorrowBox.Core/Reservations/Reservation.cs), and [Equipment.cs](../../src/BorrowBox.Core/Equipment/Equipment.cs). Read the store interfaces before their implementations. A service coordinates several contracts; a method named Save does not by itself create a transaction. Your task is to explain what a caller can observe after success, rejection, interruption and retry.

Prerequisites are deliberately small: you can read a constructor, await a Task, recognise a domain exception, and distinguish a mutable instance from a value captured from it. If async feels mysterious, first trace a single reservation without parallel requests. If you know SQL well, temporarily set transaction assumptions aside: the default stores are in-memory dictionaries of live references. The SQLite equipment adapter is a different boundary and does not make the other stores durable.

Write an operation matrix with columns for input, prerequisites, candidate construction, first visible effect, later fallible call, and returned result. For ReserveAsync, the expiry constructor check precedes EquipmentItem.Reserve. SaveAsync and reservation AddAsync follow the mutation. For CheckOutAsync, the Loan constructor precedes TryCheckOutAsync, but loan AddAsync follows it. For ReturnAsync, a valid equipment status is checked before the two entities change. These are different orderings, not interchangeable examples of one vague "validation layer."

Use three evidence levels. A domain test establishes a local rule, such as a due date not preceding the UTC checkout date. A workflow test establishes coordination across equipment and loan state. An adapter test establishes how a particular store behaves under failure or concurrency. An HTTP response can supplement them, but a correct error response alone says nothing about state already leaked through a reference.

Before running the lab, answer four diagnostic questions. Can GetAsync return the exact instance supplied to AddAsync? Which method locks a single equipment instance? Does ILoanStore expose a transaction shared with IEquipmentStore? Does a reservation have a version or expected-status compare-and-swap operation? Verify each answer in source. Current answers are yes, TryCheckOutAsync, no, and no. Those answers determine which promises your tests may honestly make.

Create a written baseline using a fixed instant and fresh IDs. Record scalar status and counts, rather than retaining a second variable pointing at the same object and calling it "before." Two variables can observe the same later mutation. Record the specific business code as well: a missing borrower and an invalid expiry may both throw BorrowBoxException, but they exercise different paths.

A useful first deliverable is six sentences, each ending with a source method: where time is captured; where date validation happens; where equipment becomes unavailable; where a loan becomes visible; where a return is rejected; and where a background expiry can leave partial progress. Do not substitute class names for behavior. Your reviewer should be able to follow those sentences without opening an architectural diagram.

Advance when you can predict state after an invalid expiry and after a failed loan-store add separately. Predicting "both fail" is insufficient: one should leave available equipment, while the latter currently leaves equipment checked out. That contrast motivates the next four sessions and prevents a green validation test from becoming an unsupported durability claim.

# 4. Validation, persistence and concurrency are different boundaries

The repaired validation ordering is valuable, but it is not rollback. Read [InMemoryEquipmentStore](../../src/BorrowBox.Infrastructure/Equipment/InMemoryEquipmentStore.cs), [InMemoryLoanStore](../../src/BorrowBox.Infrastructure/Loans/InMemoryLoanStore.cs) and [SqliteEquipmentStore](../../src/BorrowBox.Infrastructure/Equipment/SqliteEquipmentStore.cs) side by side. The first two retain domain references. SQLite maps between a row and a domain object. An exception can therefore leave different observable evidence depending on which adapter participates.

Build a fault table before proposing a fix. Include constructor rejection; cancellation on the initial read; SaveAsync failure after Reserve; loan AddAsync failure after checkout; and return SaveAsync failure after loan.Return. For each, mark in-memory state, persisted state, and the response outcome separately. The current interfaces do not provide one transaction containing an equipment change plus a reservation or loan insertion. A Save method on just one adapter cannot supply that missing contract.

Do not "rollback" by blindly setting equipment Available in a catch block. Another legitimate operation may have happened since your earlier read, or the failed adapter may have committed before its response was lost. An unconditional compensation can overwrite a valid later state. A compensation needs an operation identity, expected version and defined legal transition; a transaction needs participants that share the same storage boundary. They solve related but different problems.

The per-equipment lock in TryCheckOutAsync serialises its availability check and mutation for that one object. It prevents two successful checkouts of the same item through that method. It does not include the borrower active-loan count or loan AddAsync. Two different equipment locks can therefore protect each item correctly while the borrower limit is exceeded. The lab's interleaved store proves this with deterministic scheduling.

Reservations have another boundary: the service reads a live object and calls Reserve outside that checkout lock. Do not infer a global equipment command lock from one protected method. Likewise, cancellation is cooperative. If a token is cancelled after equipment mutation but before loan AddAsync checks it, the operation can report cancellation with a remaining effect. A future design must state whether cancellation is accepted only before commit and how callers discover a committed result after a lost response.

For a database design, place loan creation and equipment status transition in one transaction, with a conditional status update and constraints. A borrower limit needs a serialisation strategy of its own: a locked borrower counter, an appropriate isolation level, or another explicitly reasoned mechanism. Counting rows and then inserting under ordinary isolation can reproduce the same race. Include the borrower dimension in your contention test.

Evidence should name the observer. A new DbContext checks persisted state; a retained entity checks the process graph; a second process checks whether a lock is merely local. A transaction rollback can restore rows while an already-mutated tracked entity still needs reloading or discarding. Conversely, a passing live-reference assertion does not show that anything survives a restart.

Your design note should end with one narrow promise you can implement and one promise you cannot yet prove. For example: "This command commits equipment and loan in one database transaction; borrower-limit enforcement is still pending." That is more useful to the next engineer than claiming the lending workflow is now safe because invalid dates no longer leak mutations.
